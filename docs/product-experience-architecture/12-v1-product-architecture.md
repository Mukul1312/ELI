# V1 Product Architecture

This document synthesizes the recommended first-version product form for Eli.

It is not a screen spec. It is the clearest architectural recommendation for what the first product should be.

## V1 Product Form

Eli V1 should be a calm companion product built around one primary study loop.

That loop is:

- return
- orient
- commit
- work
- close
- reflect when earned

## Main Route

The main route of the product should prioritize:

1. re-entry without pressure
2. a bounded next step
3. protection of actual study
4. grounded completion

This route should dominate the experience. It is the product's center of gravity, and it should be the default path the product continuously pulls the student back toward.

## Supporting Routes

V1 should include only a very small number of supporting routes:

- setup
- preferences and boundaries
- a lightweight history view for recall, if history is needed at all

These should exist only to support the main route.

`Continuity` should not be a destination in V1. It should appear primarily as a lightweight embedded surface inside the main route, especially around return and closure.

## Mirror in V1

`Mirror` should exist in V1 as a light reflective layer, not as a major destination.

In V1:

- occasional reflective moments around return or close
- sparse reflective surfaces
- no permanent "insights" section
- no heavy reflection frequency

## What V1 Should Feel Like

If the architecture is correct, V1 should feel:

- easier to come back to than a normal study app
- clearer about what matters right now
- quieter once the student begins
- more believable at completion than typical productivity products
- reflective only when reflection is earned

## What V1 Needs Most

The first version needs these elements to be strong:

- arrival surface
- commitment surface
- active study surface
- completion surface
- embedded continuity
- careful early `Mirror` behavior

If those are strong, Eli can already deliver its core product job.

## What Exists In V1

V1 should definitely include:

- one primary return-to-study route
- the four core loop surfaces: arrival, commitment, active study, completion
- lightweight embedded continuity within the main route
- setup and boundaries support
- restrained, occasional `Mirror` moments near return or close when earned

## What Remains Secondary In V1

The following may exist only as clearly secondary support:

- a lightweight history view for recall
- preference and setup areas
- limited reflective carryover outside the main loop

None of these should compete with the core route.

## What Is Out Of Scope For V1

V1 should explicitly leave these out of scope:

- analytics-heavy continuity
- many parallel feature areas
- a dedicated insights destination
- rich reflection systems before credibility is earned
- overly expressive personalization
- large management surfaces that pull attention away from studying
- any dashboard-like review surface

## V1 Recommendation

The best first architecture for Eli is a loop-centered product with a small number of canonical surfaces, shallow navigation, and adaptive behavior driven by state, phase, and `Mirror`.

That architecture should be implemented as:

- one dominant main route
- embedded continuity, not navigated continuity
- one or two clearly secondary support routes at most
- sparse, earned `Mirror` behavior

That form is the most faithful translation of the current Eli brand system into product.

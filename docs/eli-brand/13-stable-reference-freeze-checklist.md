# Stable Reference Freeze Checklist

This document is the practical gate for treating the Eli brand folder as a stable V1 reference.

Its purpose is not to reopen the architecture. Its purpose is to confirm that the architecture is clear enough, bounded enough, and usable enough to stop behaving like a live exploration.

Use this checklist when deciding whether `docs/eli-brand/` is ready to function as the working source of truth for product, UI, copy, and future visual design work.

## 1. What Freeze Means

For V1, a freeze means:

- the core brand architecture is no longer being casually redefined
- the folder is stable enough to guide real product and design decisions
- open questions are managed explicitly rather than treated as reasons to restart the system
- future changes become controlled refinements, not ongoing conceptual drift

Freeze does **not** mean every future detail is settled forever. It means the reference is now stable enough to use with confidence.

## 2. Structural Lock Checklist

The brand system should only be frozen when these decisions are treated as locked:

- Eli has one stable identity with adaptive expression
- Eli has three operating states: `Shelter`, `Focus`, `Momentum`
- Eli has one reflective layer: `Mirror`
- Eli has three relationship phases: `Arrival`, `Attunement`, `Familiarity`
- phase progression is evidence-based, not tied to rigid session counts
- the brand adapts to student state and relationship depth, not to fixed persona categories

If any of these still feel open to casual reinterpretation, the folder is not ready to freeze.

## 3. Top-Layer Clarity Checklist

The top of the folder must be understandable in one pass.

Confirm that:

- `00-index.md` explains how the system is organized and how to read it
- `01-brand-thesis.md` behaves like the argument for Eli, not a law or execution doc
- `02-core-identity.md` behaves like the permanent law layer, not a second thesis
- `03-adaptive-expression.md` explains how identity, states, phases, and `Mirror` fit together

The test is simple: a new collaborator should be able to read `00` through `03` and explain the system without inventing missing structure.

## 4. Document Ownership Checklist

Each core document should own one layer cleanly enough that the folder does not need constant reinterpretation.

Confirm that:

- `04-brand-states.md` is about current-capacity expression, not relationship maturity
- `05-brand-phases.md` is about relationship maturity, not state behavior
- `06-visual-system.md` governs sensory and visual behavior, not product mechanics
- `07-typography-system.md` governs type roles and behavior, not a rushed final font decision
- `08-voice-and-copy.md` governs linguistic behavior, not product microcopy inventory
- `09-logo-and-asset-system.md` governs mark behavior and reduction rules, not symbolic over-explanation
- `10-product-ui-principles.md` translates brand into interface laws without becoming a full UX spec
- `11-open-questions-and-decisions.md` contains true open decisions with resolution logic, not hidden instability in the core system

If multiple docs still feel like they are doing the same job, the folder is not fully stable.

## 5. Brand-vs-Product Boundary Checklist

The folder should be frozen only if the boundary between brand docs and product UX specs is usable in practice.

Confirm that:

- brand docs define identity, expression, principles, tone, and interface laws
- product or UX specs define workflows, feature behavior, runtime logic, experiments, and implementation details
- future contributors can tell the difference without repeatedly re-debating where something belongs

If brand docs are still absorbing product mechanics or flow logic, freeze should wait.

## 6. Open Questions Threshold

The system does not need every open question resolved before freeze.

It is acceptable to freeze when unresolved items are:

- execution-facing
- validation-facing
- aesthetic tuning questions
- implementation detail questions that sit downstream of the core model

Examples of acceptable unresolved items:

- final font pairing
- final terracotta tuning
- small-size logo reduction behavior
- the exact product form of `Mirror`
- evidence thresholds for deeper familiarity

It is **not** acceptable to freeze if unresolved items still question the core architecture itself.

## 7. Change Control After Freeze

After freeze, proposed changes should be treated as one of three categories:

### 1. Clarification
Improves wording, examples, or structure without changing the system.

### 2. Application Detail
Adds guidance for usage in product, visual design, copy, or implementation contexts without changing the architecture.

### 3. Architecture Change
Alters the core model, such as identity laws, state structure, phase structure, or the role of `Mirror`.

Only architecture changes should trigger deep review. Clarifications and application details should remain disciplined and narrow.

## 8. Final Go / No-Go Test

Before freezing the folder, answer these questions directly:

1. Can a product designer use this folder to guide interface decisions without relying on legacy brand assumptions?
2. Can a copy or content designer understand how Eli should sound without needing a separate verbal brief?
3. Can a future collaborator explain the difference between identity, states, phases, and `Mirror` after one read?
4. Are the remaining open questions managed in `11-open-questions-and-decisions.md` rather than hidden inside core docs?
5. Is the folder stable enough to stop behaving like an exploration and start behaving like a working source of truth?

If the answer is yes to all five, the Eli brand system is ready to be treated as the stable V1 reference.

## 9. Freeze Recommendation

When this checklist passes, the correct next move is:

- stop broad conceptual rewriting
- use the folder as the brand source of truth
- move downstream product questions into product and UX specs
- allow only controlled refinement rather than open-ended redefinition

That is the point of freeze: not to stop thinking, but to stop drifting.
